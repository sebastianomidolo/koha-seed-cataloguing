# Plugin architecture

## Three-layer design

```
┌─────────────────────────────────┐
│   SeedCataloguing.pm            │  Koha plugin shell
│   (UI, CSRF, staging, redirect) │
└────────────────┬────────────────┘
                 │ normalised species hash
                 ▼
┌─────────────────────────────────┐
│   MARCBuilder.pm                │  Source-agnostic MARC builder
│   (hash → MARC::Record)         │
└─────────────────────────────────┘
                 ▲
                 │ normalised species hash
┌─────────────────────────────────┐
│   Source/CoL.pm                 │  Data source driver
│   (CoL API → normalised hash)   │
└─────────────────────────────────┘
```

Adding a new data source (GBIF, GRIN, iNaturalist…) means writing a new
`Source/XYZ.pm` that returns the same normalised hash. `MARCBuilder` and the
plugin shell need no changes.

---

## Normalised species hash

The bridge between source drivers and the MARC builder:

```perl
{
    scientific_name => 'Sanguinaria canadensis L.',
    common_names    => ['bloodroot'],           # English first, others after
    authority_uri   => 'https://www.catalogueoflife.org/data/taxon/79HDB',
    external_uris   => [],                      # POWO, GBIF, etc.
    source_code     => 'catl',                  # registered LoC code
    synonyms        => ['Sanguinaria ...'],
    published_in    => 'Published 1753',
    distribution    => 'Eastern North America',
    classification  => [
        { rank => 'family',  name => 'Papaveraceae' },
        { rank => 'genus',   name => 'Sanguinaria' },
        { rank => 'species', name => 'canadensis' },
        # … more ranks as available
    ],
}
```

## User workflow (four steps)

```
Step 1 — Search form
  User types: "Sanguinaria canadensis"
       ↓
Step 2 — Results list
  CoL API returns matching taxa; user picks one
  (each name links to its CoL taxon page)
  Query URL and raw JSON shown at the bottom for transparency
       ↓
Step 3 — MARC preview
  Full MARC record displayed field by field before committing
       ↓
Step 4 — Stage the record
  CSRF validated; record staged into Koha's import batch system
  → redirected to Tools > Manage staged MARC records
```

---

## Duplicate detection

The plugin does not call `AddBiblio` directly. Instead it uses Koha's native
staging workflow combined with a Record Matching Rule (**SEEDCOL**) that matches
on `110 $0` (the CoL taxon URI, indexed as the OpenSearch field `seed-col-uri`).

- Match found → record flagged `auto_match` → librarian sees candidate and decides
- No match → record flagged `no_match` → safe to commit as a new species

The matching rule uses the URI as-is with no normalisation — the OpenSearch analyzer
applies identically at index time and query time, so pre-mangling the URI would risk
a mismatch.

---

## Persistent import batch

The plugin maintains one persistent import batch across multiple staging operations
(batch id stored via `store_data`/`retrieve_data`). Each new staging call adds a
record with an incrementing `record_sequence`. The librarian commits the whole batch
at once from the manage-staged-records screen.

---

## CSRF handling

All POST forms include a CSRF token generated by `Koha::Token->new->generate_csrf`.
Koha 25.11 validates this at the framework level before the plugin code runs — all
POST forms must include the token, not only the confirm step.

---

## Plack caching rule

**Every time plugin files are updated on disk, Plack must be restarted.**

Plack workers cache `require`d modules in `%INC` for the lifetime of the worker
process. Updating a `.pm` file on disk has no effect on a running worker. Only
`seba` has sudo on the production server:

```bash
sudo koha-plack --restart lecat
```

See also: `deploy-to-lecat.sh`.
